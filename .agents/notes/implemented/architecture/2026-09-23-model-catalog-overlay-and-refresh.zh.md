# Agent Note：模型目录叠加层与显式刷新

Status: implemented

[English](2026-09-23-model-catalog-overlay-and-refresh.md) | 中文

## 问题

pi-ai 自带的路由只提供其生成目录所记录的模型，因此提供方在已安装 pi-ai 构建之后发布的模型要等更新的构建才能请求，harness 里也没有任何机制可以抓取它。按路由逐个添加这类模型需要一份 `models` 列表，而该列表会替换整条路由的目录，也无法表达混合协议的网关路由。

## 决策

`dsh-llm-pi-ai` 可以把一份公开模型目录叠加到已安装目录之上。`catalogOverlay` 指定目录（`true` 表示已发布的 models.dev 目录）以及缓存快照保持有效多久；快照位于 `$DSH_HOME/cache/llm-pi-ai/models-dev.json`，只在启动时读取，绝不按计划抓取。目录中已安装目录未描述的每个条目都会成为一个模型：其协议取自条目的 npm 包、提供方唯一的协议，或 OpenCode 网关「不带包即 Chat Completions」的约定；其端点事实——base URL、兼容开关、推理映射、标头、条目省略的容量——取自同一提供方与协议的已安装模型。已安装目录描述的 id 保留其已安装条目，没有对应已安装同类的条目会被跳过而不是猜测。

新鲜度是显式的。`LlmAdapter.refreshModels()` 重新抓取某个适配器的目录，`LlmRuntime.refreshModelCatalogs()` 对每个已注册适配器调用一次，`session.refreshModelCatalog` 用结果重建浏览器目录，模型列表搜索框旁的刷新按钮就是调用它的界面。快照解析保持同步：解析器合并当前快照，所有抓取都在带外运行。

## 考虑过的替代方案

- **周期性后台刷新。** 否决：它会在每个启用叠加层的部署里把第三方抓取放到定时器上，而实际需求是用户可以按需更新列表。
- **在解析器内部完成叠加。** 否决：`resolveRouteModels` 是同步且纯粹的，在那里做网络读取会让模型解析依赖目录的可用性。
- **由独立包负责目录抓取。** 暂缓：合并必须发生在解析器内，而抓取需要已安装目录的事实来安置条目。两部分保持为独立模块（`catalog-overlay.ts`、`catalog-sync.ts`），因此拆分仍然是机械的。
- **在 `models` 中按路由声明这些模型。** 否决：它会替换整条路由的目录，而这里要解决的模型恰好位于混合协议的网关路由上。
- **构建期生成并随包发布叠加层。** 暂缓：已安装目录本身已经提供基线，生成产物只会增加发布延迟而不会消除任何失败模式。

## 后果

启用叠加层的部署可以提供比其 pi-ai 构建更新的模型，并无需重启即可刷新；未启用的部署不受影响，因为缺省与 `false` 都表示关闭。叠加层模型继承其端点事实，因此新模型上存在差异的网关怪癖需要一条 `modelOverrides`。快照是每个 harness home 一份文件，既无缓存又无法访问目录时启动不提供任何叠加层。`LlmAdapter` 增加了一个默认空实现的方法，因此每个适配器都能回应运行时的刷新而无需自行实现。

## 测试

`catalog-overlay.ts` 与 `catalog-sync.ts` 的用例钉住映射、跳过、缓存与释放规则；真实 Loader 组合测试会提供、请求、缓存、刷新并丢弃一个叠加层模型；`LlmRuntime` 与 Session Controller 的用例覆盖该 seam 与 RPC；模型选择器的组件与浏览器用例覆盖该按钮。
